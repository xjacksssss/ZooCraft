# M10a Path Cost Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cut what visitors' movement costs: count and time real path plans and how many fall short of their target, make visitors' path search range configurable and pick its default by measurement, and stop SmartBrainLib's shortcut check running every tick. Done when, at 200 visitors in Big Park, visitors add at most 8 ms per tick over the no-visitor baseline with P99 under 50 ms, or the remaining gap is measured and assigned to M10b.

**Architecture:** M10 is split in two. M10a (this plan) is the path cost half of spec section 7.1, plus the planning findings from spec section 3.4. M10b, planned after this one is measured, covers crowding at spots, gates and counters, crowd recovery and where visitors look (spec 7.2 to 7.6). Everything here sits in `VisitorNavigation`, the visitor-only navigation subclass. It overrides `createPath` (follow range, plan statistics) and SmartBrainLib's `ExtendedNavigator.attemptShortcut` (shortcut throttling). Plan statistics reuse `TimerSlots`: a count-only slot for plans that fall short, plus a recent-calls query.

**Tech Stack:** Java 21, NeoForge 21.1.251, SmartBrainLib 1.16.11 (`SmoothGroundNavigation`, `ExtendedNavigator`), JUnit 5, GameTests, the `tools/perf` harness.

**Spec:** `docs/superpowers/specs/2026-10-15-phase3-scale-compatibility-design.md` (sections 3.4, 7.1, 8.4 and 10)

**Execution note:** Autonomous build (user memory). Native execution on branch `phase3`.

## What M9 found and how the code works

- At 200 visitors, path following (SmartBrainLib's `attemptShortcut`) costs about 7.9 ms per tick, and path planning about 7 ms (54 plans a second at about 2.6 ms each).
- `SmoothGroundNavigation.followThePath` calls `attemptShortcut(targetNode, pos)` on every tick. That method walks back from `targetNode` (the furthest node before a vertical change, often the end of a flat path) to the next node. For each node it traces the visitor's box through every block in between (`isCollisionFreeTraversal`), and jumps to the first node it can reach in a straight line. Until the visitor reaches the next node or gets a new path, the answer can't change, so re-running it every tick is waste.
- `PathNavigation` is built with `maxVisitedNodes = followRange × 16` = 768, and `createPath` searches no further than `followRange` (48 blocks) from the visitor. A target further away in a 240-block park can never be reached in one plan, so the search uses its whole node budget and returns a partial path. SmartBrainLib's `MoveToWalkTarget.attemptNewPath` then plans a second time, towards a random position nearer the target (`DefaultRandomPos.getPosTowards`). Partial paths end before the target, so they are re-planned again and again on a long walk.

## Global Constraints

- New config keys go in the existing `simulation` section and are read live: `visitorFollowRange` (default decided in Task 4; range 16 to 128) and `pathShortcutMode` (`EVERY_NODE` default, `EVERY_TICK`, `OFF`).
- `pathShortcutMode = EVERY_TICK` must behave exactly like SmartBrainLib today, so the change can be compared and undone from config.
- Only the visitors' navigation changes. Other mobs are untouched.
- A "plan" is a real search. Calls where vanilla reuses the current path (same target, path not done) are not counted or timed as plans.
- Movement must look the same: visitors still cut straight across open ground and round corners on paths.

## Review Focus

- **A follow-range change while visitors are mid-walk.** The next plan uses the new range, and nothing crashes or leaves a visitor without a path. Task 2 pins this with a GameTest that changes the range between two plans.
- **A visitor whose path is replaced mid-way** (new target, or a re-plan after failure). The shortcut throttle must try again on the new path straight away, not wait for a node index that happens to match the old path's. Task 3 pins this with a GameTest that swaps the path and checks a shortcut is attempted.
- **A path with a single remaining node, or a path that is done.** The shortcut override must not throw or loop. Task 3 calls it on a finished path in the GameTest.
- **`OFF` mode.** Visitors still reach targets, node by node. Task 3's walking test also runs with `OFF`.
- **Very large ranges (128) in a small zoo.** No error, and the cost is visible in `/zoo debug perf`. Task 4 measures 128.

```java
package com.zoocraft.visitor;

/** When visitors try to cut corners on their path (Phase 3 spec section 7.1). */
public enum ShortcutMode {
    /** When the visitor reaches a new path node or gets a new path. */
    EVERY_NODE,
    /** Every tick: SmartBrainLib's own behaviour. */
    EVERY_TICK,
    /** Never: follow the path node by node. */
    OFF
}
```

```java
                .defineEnum("pathShortcutMode", com.zoocraft.visitor.ShortcutMode.EVERY_NODE);
```

`VisitorNavigation`: declare `implements ExtendedNavigator` (redundant with the superclass, but required so the class can call `ExtendedNavigator.super.attemptShortcut`), and add:

```java
    private @Nullable Path shortcutPath;
    private int shortcutNode = -1;
    private int shortcutAttempts;

    /**
     * SmartBrainLib tries to skip ahead along the path on every tick, tracing the visitor's box through every block
     * to each later node. The answer only changes when the visitor reaches a new node or gets a new path, so in
     * {@link ShortcutMode#EVERY_NODE} it only tries then.
     */
    @Override
    public boolean attemptShortcut(int targetNode, Vec3 entityPosition) {
        ShortcutMode mode = ZooConfig.PATH_SHORTCUT_MODE.get();
        if (mode == ShortcutMode.OFF || path == null || path.isDone()) {
            return false;
        }
        if (mode == ShortcutMode.EVERY_NODE && path == shortcutPath && path.getNextNodeIndex() == shortcutNode) {
            return false;
        }
        shortcutAttempts++;
        boolean skipped = ExtendedNavigator.super.attemptShortcut(targetNode, entityPosition);
        shortcutPath = path;
        shortcutNode = path.getNextNodeIndex();
        return skipped;
    }

    /** Real shortcut attempts so far, for tests. */
    public int shortcutAttempts() {
        return shortcutAttempts;
    }
```

Import `net.tslat.smartbrainlib.api.core.navigation.ExtendedNavigator` and `net.minecraft.world.phys.Vec3`. The index is recorded after the attempt, so a successful shortcut (which moves the index) doesn't trigger a second attempt on the next tick. The next attempt comes when `followThePath` advances to a further node.
